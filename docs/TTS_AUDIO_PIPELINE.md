# OOM TTS Audio Pipeline

## What We Use

| Tool | Role |
| --- | --- |
| Kokoro-82M | local AI TTS model that computes real audio from text |
| `kokoro-js` | browser/dev runner for Kokoro model inference |
| WaveSurfer | audio player and waveform renderer |
| FFmpeg + ffprobe | developer-machine WebM/Opus encoding and asset validation |
| `speechSynthesis` | immediate final fallback provided by the operating system/browser |

OOM product voices are locked to Heart, Bella, Sarah, and Sky. Their IDs are `af_heart`, `af_bella`, `af_sarah`, and `af_sky`.

## Why Fixed Content Is Pre-generated

System Web Speech uses an OS/browser voice that is already available, so it can speak immediately. Its voice differs by environment and it does not provide the same repository-owned audio Blob, codec, duration, or waveform control.

Kokoro inference produces consistent real audio that OOM can play as a Blob and visualize accurately. That computation takes time. In the development benchmark, long q8/WASM generation was slower than real time. An isolated fp32/WebGPU run was much faster, but still left a noticeable Play wait; WebGPU streaming was not measured as a production-ready replacement.

The current fixed corpus is enumerable at build/development time. Pre-generating it therefore gives immediate playback, consistent voices, real waveform peaks, and no model load on a static hit.

The full decision is recorded in [ADR 001](decisions/001-static-first-tts.md).

## Runtime Flow

```text
text + selected voice
→ normalize text
→ SHA-256 hash
→ load production static manifest
   ├─ hit: WebM/Opus URL + precomputed peaks
   └─ miss or media failure
      → lazy Kokoro browser runtime
         ├─ success: WAV Blob + runtime waveform/cache
         └─ failure: system Web Speech
```

`src/lib/tts/staticTts.ts` resolves base-safe URLs using `import.meta.env.BASE_URL`. Runtime accepts only `public/generated-tts/tts-manifest.json` when its coverage is complete and its model/profile/normalization/voice contract matches. It never uses the staging manifest.

`src/lib/tts/TtsManager.ts` owns the fallback order and runtime cache. Static files are not duplicated in IndexedDB. Runtime-generated Kokoro WAV may use bounded memory and optional IndexedDB LRU caches; cache/private-mode/quota failures are optimization failures and must not break playback.

## Surface Contracts

- **STEP 3:** resolves the exam and script preview phrases for their selected voices and shows seekable waveform players.
- **STEP 4:** resolves canonical Level script audio and the self-introduction example, shows a real waveform before Play when static coverage exists, and permits seeking/replay.
- **STEP 5:** resolves each Level-specific roleplay answer example with the script voice.
- **STEP 6:** pre-resolves a question (or the one-time self-introduction warm-up) without consuming a listen. Playback is non-seekable, fixed at 1.00×, and consumes at most two listens.

All synthesis assets are produced at `1.00×`. STEP 4 and STEP 5 speed changes only WaveSurfer `playbackRate` with pitch preservation. Playback rate is excluded from static and runtime cache identity.

## Generated Inputs and Runtime Assets

| Path | Policy |
| --- | --- |
| `artifacts/tts-inventory.json` | generated by `npm run tts:audit`, tracked, direct generator/validator input, do not hand-edit |
| `docs/generated/tts-inventory.md` | generated local audit report, ignored, not a runtime or build input |
| `public/generated-tts/audio/<textHash>/<voice>.webm` | generated runtime asset, tracked |
| `public/generated-tts/audio/<textHash>/<voice>.peaks.json` | 256 PCM-derived peaks and duration metadata, tracked with audio |
| `public/generated-tts/tts-manifest.json` | production-complete runtime manifest, tracked |
| `public/generated-tts/tts-manifest.staging.json` | resumable/dev status output, ignored, never read by runtime |

The current production snapshot contains 177 unique playable texts × 4 locked voices = 708 audio targets, including the shared self-introduction prompt and three Level examples. These numbers are a generated snapshot, not an architectural constant. When content grows, update the audit and intentionally update the expected coverage contract in `scripts/static-tts-assets.mjs` only after reviewing the new inventory.

Do not hand-edit audio, peaks, inventory, or manifest metadata. Audio and peaks must move together. The production manifest is promoted only after exact expected coverage is valid.

## Generation Pipeline

```text
active Course/Level data + voice previews
→ `npm run tts:audit`
→ `artifacts/tts-inventory.json`
→ `npm run tts:generate`
→ browser Kokoro fp32/WebGPU when available
   or q8/WASM fallback
→ uploaded PCM WAV
→ local FFmpeg WebM/Opus 64 kbps mono
→ ffprobe metadata validation
→ 256 real PCM peaks
→ staging manifest
→ production manifest when complete
```

`scripts/audit-tts-inventory.mjs` loads the active registry through Vite, so it audits discovered Course bundles rather than legacy top-level data. `scripts/generate-static-tts.mjs` scans all existing targets before opening the generator. A valid unchanged target is a hit and is not synthesized again.

FFmpeg tools are resolved from `OOM_FFMPEG_PATH` / `OOM_FFPROBE_PATH`, system `PATH`, or supported local discovery. WAV and intermediate WebM/peaks temp files are removed in `finally`; interrupted dot-prefixed intermediates are ignored by Git.

## Content Update Procedure

For a changed script, roleplay example, practice question, or preview phrase:

1. Run `npm run tts:audit`.
2. Inspect inventory text/hash/source changes.
3. If total coverage changed, update the explicit expected text/target/category assertions in `scripts/static-tts-assets.mjs` after reviewing the inventory.
4. Run `npm run tts:generate`; its initial scan skips valid targets and identifies missing/invalid ones.
5. After the generator reports complete coverage, run `npm run tts:validate -- --prune-dry-run`.
6. Review inventory, production manifest, new audio/peaks, and dry-run output together.

Do not run actual prune without explicit authorization. Git history preserves removed snapshots, but a validator dry-run is required before any generated runtime asset becomes a deletion candidate. Validation intentionally withdraws the production manifest when coverage is incomplete, so do not use it as a harmless pre-generation probe after changing content.

## Dynamic AI Text

AI-generated or user-entered text is not enumerable and normally misses the static manifest. It follows the runtime path. Current browser Kokoro can be too slow for immediate product UX on long dynamic text, so system Web Speech may be offered or used as the immediate fallback.

A future intranet GPU or TTS server may handle dynamic text. Fixed Course content can remain static-first; moving to a backend is optional, not a prerequisite.

## Benchmark Evidence and Limits

The decision used a 968-character Bella script at synthesis 1.00× as a configuration-specific sanity check:

- q8/WASM total generation was about 112 seconds;
- q8 streaming produced first audio at about 16.5 seconds but had repeated underruns;
- isolated fp32/WebGPU total generation was about 18.5 seconds;
- WebGPU streaming was not measured.

These values explain the current static-first choice; they are not a universal device performance promise. The one-off benchmark UI was removed after the decision. Future performance work should add a scoped, reproducible benchmark with environment metadata instead of treating these numbers as a production default.
